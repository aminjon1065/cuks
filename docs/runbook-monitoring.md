# Мониторинг — runbook администратора

Мониторинг платформы CUKS состоит из трёх слоёв (docs/08-deployment.md §Мониторинг, docs/modules/16 §7,
задача 7.3):

1. **Health-дашборд в админке** (`/app/admin/health`, право `admin.system.monitor`) — «взгляд одним
   глазом»: статусы сервисов, размеры БД/бакета/диска, очереди BullMQ, последний бэкап, ошибки за 24 ч,
   регламентные развёртки worker'а.
2. **Uptime Kuma** — собственно мониторинг: периодические пинги сервисов и алерты.
3. **Алерты в чат-канал** — Uptime Kuma шлёт вебхук в API, тот постит системное сообщение в канал.

## 1. Health-дашборд

Открывается суперадмином/администратором платформы в разделе «Здоровье». Обновляется каждые ~15 c. Виджеты:

- **Сервисы** — восемь проб api→postgres/redis/minio/geoserver/martin/livekit/clamav и
  `docflow_exchange` («Обмен документами», `HEALTH_SERVICES`). `Не настроен` — сервис не
  сконфигурирован (например, LiveKit без `LIVEKIT_URL`), это не падение: такие пробы исключены из
  общего статуса.
- **Хранилище** — размер БД (`pg_database_size`) с разбивкой по схемам, объём и число объектов в бакете
  MinIO, свободное место на ФС контейнера api. Диск контейнера — лишь ориентир; реальный диск данных
  следит Uptime Kuma / хост.
- **Очереди задач** — waiting/active/delayed/failed/completed по каждой очереди BullMQ; при `failed > 0` —
  кнопка «Повторить» (перезапускает упавшие задачи очереди).
- **Регламентные развёртки** — последний прогон каждого из трёх плановых заданий worker'а:
  «Сроки документов» (`deadlines`), «Сроки хранения» (`retention`), «Обслуживание журнала аудита»
  (`audit-maintenance`): когда закончился, сколько шёл, что насчитал, не упал ли. Ниже.
- **Последний бэкап** — по маркеру, который пишет `backup.sh` после успешного restic-снапшота.
- **Ошибки за 24 ч** — счётчик 5xx (почасовые корзины в Redis, суммируются за сутки).

Дашборд НЕ заменяет мониторинг — он не шлёт алертов и не хранит историю. Для этого — Uptime Kuma.

### 1.1. Регламентные развёртки (плановые проходы worker'а)

Очереди отвечают на вопрос «есть ли необработанные задания», но не на «случился ли сегодняшний
проход». Repeatable job, который упал, BullMQ переспрашивает и убирает из `failed`; проход, которого
не было (worker лежал в свой слот), не оставляет следа нигде — пропущенный слот не догоняется. Поэтому
worker по завершении каждого прохода пишет запись в Redis (`metrics:jobrun:<задание>`, TTL 45 суток —
заведомо длиннее самого длинного порога устаревания, см. ниже), а дашборд её показывает. Контракт — `packages/shared/src/metrics/index.ts`, подробности —
`docs/modules/16-admin.md` §7.

| Состояние (бейдж) | Что означает | Что делать |
|---|---|---|
| `ok` — «Норма» | проход **дошёл до конца** и не старше своего порога. Не «всё удалось»: сбой на отдельном элементе (одна резолюция, один узел корзины) ловится, пишется в лог и проход идёт дальше — такой проход тоже «Норма» | ничего. Нули в счётчиках прохода — законный результат: «нечего было делать». Если ждали работы, а её не видно, — частные отказы искать в логе: `dc logs worker --since 24h \| grep -E "item failed\|skipping"` |
| `failed` — «Сбой» | процессор бросил исключение (текст ошибки — в самой карточке) | смотреть лог worker'а по этому заданию; BullMQ мог переспросить задание уже после записи |
| `stale` — «Давно не выполнялась» | проходы прекратились | `dc ps worker`, лог worker'а. Последствия по каждому заданию — `docs/runbook-docflow.md` §7 |
| `unknown` — «Нет данных» | записи о прогоне нет вовсе, либо Redis недоступен на чтение (тогда `unknown` сразу у всех трёх заданий и красна проба redis) | штатно — до первого прогона после установки или очистки Redis: суточные ждут ночного слота, `audit-maintenance` отчитывается уже при старте worker'а (`ensure` ставится и на старт, и по расписанию). Дольше — разбирать как `stale` |

`failed` или `stale` хотя бы у одного задания переводят **общий** статус экрана в «Есть проблемы»
(`degraded`); до «Недоступно» проходы не опускают никогда — это состояние оставлено за сервисами.
`unknown` общий статус не портит, чтобы свежая установка не светилась жёлтым до первой ночи.

Пороги устаревания заданы по расписанию каждого задания, а не общей константой:

| Задание | Расписание | Порог |
|---|---|---|
| `deadlines` | `0 8 * * *`, tz `Asia/Dushanbe` | 26 ч |
| `retention` | `0 3 * * *` (по времени процесса worker'а) | 26 ч |
| `audit-maintenance` | `0 3 1 * *` — раз в месяц | 792 ч (33 суток) |

Месячному заданию общий суточный порог оставлял бы «Давно не выполнялась» двадцать девять дней из тридцати —
это не мониторинг, а тренировка не смотреть на экран.

Учёт не может испортить измеряемую работу: запись прогона не бросает исключений и не отклоняется —
недостучавшийся Redis только пишет строку в лог worker'а (`failed to record job run metrics`).
Поэтому его недоступность никогда не даёт `failed`. Что она даёт:

- **Redis недоступен на чтение** (в момент открытия экрана) — `unknown` сразу у всех трёх заданий;
  одновременно краснеет проба redis в «Сервисах», по ней это и опознаётся.
- **Запись не долетела**, а прошлая цела — на экране остаётся прошлый прогон. Он сначала перешагнёт
  свой порог и станет `stale` (для суточных заданий — через 26 ч), и лишь много позже, по TTL в
  45 суток, исчезнет совсем и станет `unknown`. Порядок именно такой и задан намеренно: TTL длиннее
  самого длинного порога (792 ч), иначе месячное `audit-maintenance` уходило бы из «Нормы» прямо в
  «Нет данных», минуя «Давно не выполнялась», — то есть встав, выглядело бы как никогда не
  запускавшееся.

`unknown` — это «не записано ни разу» или «Redis не отвечает», а не «запись протухла»: запись живёт
45 суток от прогона, а жёлтой карточка становится задолго до этого — у суточного задания она
светится к моменту исчезновения записи 44 суток, у месячного 12 (45 суток TTL минус его порог в
33). Порядок соблюдается у всех трёх — сначала жёлтая карточка, потом «Нет данных», — но запас у
месячного самый малый, из-за него TTL и выбран. Обратное направление ошибки — объявить упавшим проход,
который отработал, — было бы хуже отсутствия панели.

Панель хранит только последний прогон, истории длительностей у неё нет и алертов она не шлёт. Если
нужен алерт на «проход не случился» — это push-монитор Kuma (§2), а не дашборд.

## 2. Uptime Kuma

Контейнер `uptime-kuma` уже в `compose.prod.yaml`. Его UI намеренно **не** выставлен наружу (порт слушает
только `127.0.0.1:3001`), чтобы консоль мониторинга не торчала в сеть. Настройка — через SSH-туннель.

```bash
# С рабочей машины админа:
ssh -L 3001:127.0.0.1:3001 <user>@<server>
# затем открыть http://localhost:3001 в браузере
```

При первом входе задать логин/пароль администратора Kuma (хранится в томе `uptimekuma`).

### Мониторы (Add New Monitor)

Kuma в сети `cuks_default`, поэтому обращается к сервисам по именам. Рекомендуемый набор:

| Тип | Имя | Проверка |
|---|---|---|
| HTTP(s) | API готовность | `http://api:3000/api/health/ready` — 200 когда всё ок; 503 при деградации зависимостей |
| HTTP(s) | MinIO | `http://minio:9000/minio/health/live` |
| HTTP(s) | GeoServer | `http://geoserver:8080/geoserver/web/` |
| HTTP(s) | Martin | `http://martin:3000/health` |
| TCP Port | PostgreSQL | `postgres:5432` |
| TCP Port | Redis | `redis:6379` |
| TCP Port | LiveKit | `livekit:7880` |
| TCP Port | ClamAV | `clamav:3310` |

Отдельно можно добавить дисковый монитор хоста (push-монитор + cron-скрипт `df`) — по вкусу.

## 3. Алерты в чат-канал

Uptime Kuma при падении/восстановлении монитора вызывает вебхук API, который постит системное сообщение в
заранее выбранный канал (например, «Дежурная смена» или служебный «Мониторинг»).

### Настройка API

1. Создать/выбрать чат-канал для алертов, скопировать его id.
2. В `.env` задать:
   - `MONITORING_ALERT_CHANNEL_ID=<id канала>`
   - `MONITORING_WEBHOOK_SECRET=<секрет>` (`openssl rand -hex 24`).
3. Перезапустить api: `dc up -d api`. Без обеих переменных эндпоинт `/api/monitoring/alert` отключён (404).

### Настройка уведомления в Kuma

Settings → Notifications → Add → тип **Webhook**:

- **Post URL**: `http://api:3000/api/monitoring/alert`
- **Request Body**: `Preset - application/json` (Kuma пошлёт `{ msg, monitor, heartbeat }`).
- **Additional Headers**:
  ```json
  { "X-Monitoring-Secret": "<тот же MONITORING_WEBHOOK_SECRET>" }
  ```

Привязать это уведомление ко всем мониторам (в каждом мониторе включить notification). Проверка — кнопка
«Test» в настройке уведомления: в канале должно появиться системное сообщение. Неверный/пустой секрет → API
отвечает 403 и сообщение не постится; при выключенном эндпоинте — 404.

> Безопасность: секрет сравнивается на сервере в постоянном времени; эндпоинт `@Public` (машинный вызов,
> без сессии/CSRF), единственный гейт — заголовок-секрет. Держите `MONITORING_WEBHOOK_SECRET` в `.env`
> (chmod 600), не логируйте.
