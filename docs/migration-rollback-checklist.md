# Чеклист миграции и отката — СЭД 2.0

Перенос изменений трека СЭД 2.0 (миграции `0047`…`0060`) на **уже работающую** установку и порядок
отхода назад, если что-то пошло не так.

Область: только этот трек. Общая установка «с нуля» — `docs/runbook-install.md`, бэкапы и
восстановление — `docs/runbook-backup.md`, стратегия схемы — `docs/plan/sed_plan_implementation.md`
§11. Инварианты миграций — `CLAUDE.md` §2.

Все команды — из корня репозитория с алиасом из `docs/runbook-install.md` §4:

```bash
alias dc='docker compose --env-file .env -f infra/docker/compose.prod.yaml'
```

Главное, что нужно понимать до начала: **drizzle-kit не генерирует down-миграций, и в
`packages/db/migrations/` их нет.** Откат в этой системе — это восстановление из бэкапа или
исправление вперёд. См. §5.

## 1. Перед миграцией

1. **Бэкап снят и ПРОВЕРЕН.** Не «бэкап запускался ночью», а именно проверенный. Порядок:

   ```bash
   dc exec backup backup.sh          # разовый бэкап вне расписания
   dc exec backup restic snapshots   # убедиться, что снапшот появился
   ```

   Проверка восстановления — на отдельной чистой VM по `docs/runbook-backup.md` §Restore-drill,
   и обязательно с шагом 6 этого раздела:

   ```bash
   docker run --rm --network cuks_default --env-file .env \
     -v cuks_miniodata:/data/minio:ro \
     cuks-backup restore-verify.sh
   ```

   `infra/scripts/restore-verify.sh` проверяет ровно то, что важно для СЭД: таблицы трека на
   месте и реестр не пуст, `document_files` не ссылается на исчезнувшие `fs_nodes`, у выборки
   версий файлов (по умолчанию 200 свежих; `VERIFY_SAMPLE=0` — все) есть объекты в бакете, и
   **счётчики регистрации не отстали** от уже выданных номеров. Ненулевой код возврата — миграцию
   не начинать. Успешный `restore.sh` сам по себе ничего не доказывает: он означает, что дамп
   применён и тома скопированы, а не что БД и объектное хранилище согласованы.

   > Если у вас настроен контур обмена (`DOCFLOW_EXCHANGE_DIR`) — учтите, что каталог обмена
   > **не входит в бэкап**: `infra/scripts/backup.sh` копирует `/data/minio`, `/data/geoserver`,
   > `/data/ca`, `/data/caddy` и дамп БД, и больше ничего; в `infra/docker/compose.prod.yaml`
   > этого каталога нет вовсе. Добавьте его в набор бэкапа сами, иначе восстановление БД
   > рассинхронизирует реестр входящих и папки `in/done/rejected` (см. §5).

2. **Зафиксировать текущую версию схемы.** Записать в журнал работ (и продублировать вне сервера):

   ```bash
   git -C <путь-к-репо> rev-parse HEAD        # версия кода ДО обновления
   ```

   и последнюю применённую миграцию из БД (запрос — в п. 3).

3. **Прочитать список применённых миграций из БД.** drizzle-kit ведёт свой журнал в отдельной
   служебной таблице. В `packages/db/drizzle.config.ts` её имя **не переопределено**, то есть
   используется значение по умолчанию drizzle-kit; в репозитории оно нигде не зафиксировано, и
   гадать не нужно — найдите её:

   ```bash
   dc exec -T postgres psql -U cuks -d cuks -c \
     "SELECT table_schema, table_name FROM information_schema.tables WHERE table_name LIKE '%drizzle%';"
   ```

   и прочитайте содержимое найденной таблицы (в ней хранятся хеш миграции и `created_at`):

   ```bash
   dc exec -T postgres psql -U cuks -d cuks -c \
     "SELECT * FROM <schema>.<table> ORDER BY created_at DESC LIMIT 20;"
   ```

   Сопоставление с именами файлов — по порядку записей и по
   `packages/db/migrations/meta/_journal.json`: в нём `idx`/`tag`/`when` для каждой миграции.
   Целевое состояние после этого обновления — `idx: 60`, `tag: 0060_modern_stellaris`.

   Независимая проверка «доехали ли структуры трека» (не требует служебной таблицы):

   ```bash
   dc exec -T postgres psql -U cuks -d cuks -c \
     "SELECT to_regclass('app.document_exchange_inbound') IS NOT NULL AS m0059,
             to_regclass('app.archive_disposition_batches') IS NOT NULL AS m0054,
             to_regclass('app.resolution_proposals') IS NOT NULL AS m0051;"
   ```

4. **Оценить объём таблицы `app.documents`.** От него зависит длительность окна: миграция `0056`
   переписывает таблицу целиком (§3, строка 0056).

   ```bash
   dc exec -T postgres psql -U cuks -d cuks -c \
     "SELECT count(*) AS docs, pg_size_pretty(pg_total_relation_size('app.documents')) AS size FROM app.documents;"
   ```

5. **Окно обслуживания.** Обновление не rolling: api и worker останавливаются (§2). Оценка окна —
   сборка образов (5–15 мин на первой сборке, `docs/runbook-install.md` §5) + миграции + smoke.
   Планировать вне рабочего дня канцелярии по Asia/Dushanbe: во время окна нельзя ни
   зарегистрировать входящий, ни отправить исходящий. Заранее предупредить делопроизводителей —
   документ, пришедший в окно, регистрируется бумажно и вводится после.

6. **Дежурные на связи.** До начала записать поимённо и проверить, что каждый доступен:
   - тот, кто выполняет команды (доступ по SSH к серверу, `.env`, право `docker compose`);
   - тот, кто принимает решение об откате (владелец данных со стороны заказчика);
   - тот, у кого есть **офлайн-копия `RESTIC_PASSWORD`** — без неё бэкап не восстановить, и это
     не тот момент, когда его стоит искать (`docs/runbook-backup.md`, врезка о пароле);
   - представитель канцелярии для проверки после применения (§4, п. 3 — регистрация в тестовом
     журнале выполняется под реальной ролью, а не «под админом»).

7. **Проверить, что для проверок §4 есть чем воспользоваться.** Нужен тестовый журнал. Создание
   журнала (`POST /api/v1/docflow/journals`) требует права `docflow.journals.manage`. **Проверьте
   по коду устанавливаемого релиза**, кому оно достаётся, — источник истины один,
   `ROLE_TEMPLATES` в `packages/shared/src/permissions/index.ts`:

   ```bash
   grep -n "docflow.journals.manage" packages/shared/src/permissions/index.ts
   ```

   В текущем состоянии кода право выдают два шаблона роли — `clerk` («Делопроизводитель») и
   `platform_admin` («Администратор платформы», вместе с `docflow.use`); плюс `superadmin` получает
   его через wildcard. То есть тестовый журнал заводится под делопроизводителем, а не под
   superadmin. Проверять по коду всё равно нужно: в более ранних сборках трека право не выдавал
   **ни один** шаблон роли, и там тестовый журнал приходилось либо искать среди уже заведённых,
   либо создавать учётной записью superadmin. И учтите: новые строки `role_permissions` попадают в
   **уже работающую** базу только при запуске `pnpm db:seed` (`seedRoles`, `packages/db/src/seed.ts`,
   дописывает недостающие права шаблонов через `onConflictDoNothing` и никогда ничего не удаляет).
   Порядок §2 сид не запускает, поэтому на существующей установке роль может остаться без права,
   пока сид не прогнали, — проверяйте не только код, но и фактические права роли в базе.
   Чего бы ни показал `grep`, **выдавать право вручную «на время миграции» не нужно** — это
   отдельное решение о ролях, а не шаг обновления.

## 2. Порядок применения

Команды сверены с `package.json` (корень) и `packages/db/package.json`. `pnpm db:migrate` в корне
разворачивается в `pnpm --filter @cuks/db migrate`, то есть `drizzle-kit migrate`.

```bash
# 0) Разовый бэкап уже снят и проверен (§1.1). Если нет — вернуться в §1.

# 1) Код
git pull
git checkout <release-tag>

# 2) Сборка образов (SPA вшивается в образ caddy)
dc build api worker caddy

# 3) ОСТАНОВИТЬ приложение — до миграций
dc stop api worker
```

**Почему останавливаем, хотя `docs/runbook-install.md` §11 этого не требует.** Обычное обновление
там rolling: миграции применяются при работающем api. Для этого трека так делать нельзя. Миграция
`0056` выполняет `ALTER TABLE app.documents DROP COLUMN search_tsv` + `ADD COLUMN … GENERATED ALWAYS
… STORED` — это переписывание всей таблицы под `ACCESS EXCLUSIVE`. Работающий api будет держать на
`documents` свои блокировки, миграция встанет в очередь и заблокирует всех остальных. Кроме того
`0055` — массовый `UPDATE` по архивным документам, и одновременная работа пользователей в архиве в
этот момент не нужна никому.

```bash
# 4) Миграции
dc run --rm api pnpm db:migrate
```

`drizzle-kit migrate` применяет только недостающие файлы, сверяясь со своей служебной таблицей;
повторный запуск после успешного — no-op.

```bash
# 5) Бэкфилл файлов документов (идемпотентен, сначала вхолостую)
dc run --rm api pnpm --filter @cuks/db backfill:docflow-files -- --dry-run
dc run --rm api pnpm --filter @cuks/db backfill:docflow-files -- --batch=200
```

`packages/db/src/scripts/backfill-docflow-files.ts` переносит файлы уже зарегистрированных
документов из личного пространства загрузившего в системное дерево `system/docflow/<documentId>/`.
Он трогает только те связи, чей узел ещё вне дерева, — второй запуск ничего не делает; коммитит по
одному документу, поэтому прерванный запуск продолжается простым перезапуском, курсора нет.

```bash
# 6) Поднять приложение
dc up -d api worker caddy
dc ps                       # все running/healthy
dc logs -f api              # первые минуты — глазами
```

**Порядок остановки и старта:** останавливаем `api` и `worker` (шаг 3) → БД (шаг 4–5) → поднимаем
`api`, `worker`, `caddy` (шаг 6). `caddy` останавливать не нужно и не следует: он отдаёт SPA и
терминирует TLS; пока api лежит, пользователи получают понятную ошибку сети вместо недоступного
домена. `postgres`, `redis`, `minio` не трогаем вообще.

**Martin.** Перезапуск (`dc restart martin`) для этого трека **не требуется**. Martin кэширует
каталог слоёв на старте, и перечитывать его нужно после изменений в источниках карты; ни одна
миграция `0047`…`0060` карты не касается — все они в схеме `app`, а MVT-функции последний раз
менялись в `0046`. Если в том же окне вы прогоняете `pnpm db:seed` или другие геомиграции —
перезапуск нужен, по `docs/runbook-install.md` §6.5.

**Порядок по §11 плана** (`additive DB → API/worker → web → backfill → constraints`) здесь
схлопнут: web вшит в образ caddy и не может ехать отдельно от api, а собственных `constraints`-шагов
после бэкфилла в треке нет. Единственное отступление от «additive DB» — `0056`, и именно из-за него
окно с остановкой.

«если написать обратную SQL вручную, потеряем ли мы что-то, чего нет больше нигде».
`ADD COLUMN`/`CREATE TABLE`/`CREATE INDEX` структурно обратимы (`DROP`), но вместе со структурой
уходит всё, что в неё успели записать после релиза, — это отмечено отдельно.

## 4. Проверка после применения

Выполнять по порядку; первый же провал — повод не пускать пользователей.

1. **Живость и готовность.**

   ```bash
   curl -fsS https://<домен>/api/health         # liveness → { "status": "ok", "uptimeSeconds": N }
   curl -fsS https://<домен>/api/health/ready   # readiness → все зависимости up; иначе HTTP 503
   ```

   `/api/health` и `/api/health/ready` — version-neutral (без `/v1`), публичные.
   Панель администратора: `GET /api/v1/admin/health` (право `admin.system.monitor`) — там же
   состояние очередей и состояние контура обмена (не настроен — штатное состояние, из общего
   статуса исключается).

2. **Схема доехала.** Повторить запросы из §1.3 — служебная таблица drizzle-kit должна показывать
   `0060_modern_stellaris` последней, `to_regclass` — не `NULL` по всем трём таблицам.

3. **Регистрация в тестовом журнале.** Под учётной записью с правом `docflow.register` (шаблон
   роли `clerk`), а не под superadmin — иначе проверка не проверяет прав. В UI: зарегистрировать
   входящий в тестовом журнале, убедиться, что номер выдан и карточка открывается. API-эквивалент:
   `POST /api/v1/docflow/documents/register-incoming`.

   Затем повторить **тот же запрос с тем же ключом идемпотентности** — должен вернуться тот же
   документ, а не второй номер (это проверяет `0047`).

4. **Счётчики согласованы.** Тот же инвариант, что проверяет `restore-verify.sh` §4: сумма
   `journal_counters.last_seq` по журналу не должна быть **ниже** количества уже выданных в нём
   номеров. Счётчик ниже выданного номера означает, что следующая регистрация выдаст дубль, и
   узнает об этом только организация, получившая оба письма.

   ```bash
   dc exec -T postgres psql -U cuks -d cuks -c "
     WITH used AS (
       SELECT journal_id, count(*) AS issued FROM app.documents
       WHERE journal_id IS NOT NULL AND reg_number IS NOT NULL GROUP BY journal_id
     ), held AS (
       SELECT journal_id, sum(last_seq) AS counted FROM app.journal_counters GROUP BY journal_id
     )
     SELECT used.journal_id, used.issued, coalesce(held.counted, 0) AS counted
     FROM used LEFT JOIN held ON held.journal_id = used.journal_id
     WHERE coalesce(held.counted, 0) < used.issued;"
   ```

   Ожидаемый результат — **пустая выборка**. Непустая — пользователей не пускать.

5. **Поисковый индекс наполнен.** Проверяется и колонка, и её GIN-индекс (это `0056`).

   ```bash
   # (а) колонка на месте, генерируемая и хранимая
   dc exec -T postgres psql -U cuks -d cuks -c \
     "SELECT attname, attgenerated FROM pg_attribute
       WHERE attrelid = 'app.documents'::regclass AND attname = 'search_tsv';"
   #    ожидаем одну строку, attgenerated = 's' (stored)

   # (б) GIN-индекс существует и валиден
   dc exec -T postgres psql -U cuks -d cuks -c \
     "SELECT i.indisvalid, i.indisready, am.amname
        FROM pg_index i
        JOIN pg_class c ON c.oid = i.indexrelid
        JOIN pg_am am ON am.oid = c.relam
       WHERE c.relname = 'documents_search_idx';"
   #    ожидаем indisvalid = t, indisready = t, amname = gin

   # (в) индекс НАПОЛНЕН, а не просто создан: пустых векторов у документов с темой быть не должно
   dc exec -T postgres psql -U cuks -d cuks -c \
     "SELECT count(*) FILTER (WHERE search_tsv IS NULL OR search_tsv = ''::tsvector) AS empty,
             count(*) AS total
        FROM app.documents WHERE deleted_at IS NULL AND coalesce(subject, '') <> '';"
   #    ожидаем empty = 0
   ```

   Затем — живой поиск в UI (или `GET /api/v1/docflow/search?...`, право `docflow.use`): найти по
   слову из темы уже существующего документа и по фрагменту его регистрационного номера. Если
   колонка есть, а поиск не находит ничего — это не индекс, это конфигурация словаря
   (`to_tsvector('russian', …)`); разбираться до пуска пользователей.

6. **Файлы документов на месте.** Скачать вложение у документа, зарегистрированного **до**
   обновления (проверяет бэкфилл §2.5: файл переехал в `system/docflow/…`, ссылка должна
   продолжать работать). Затем — приложить новый файл к новому документу и скачать его.

7. **Архив не потерял сроки.** Открыть опись архива и убедиться, что у документов, подшитых **до**
   обновления, проставлены дата подшивки и срок хранения (это результат `0055`):

   ```bash
   dc exec -T postgres psql -U cuks -d cuks -c \
     "SELECT count(*) FROM app.documents
       WHERE status = 'archived' AND archived_at IS NULL AND deleted_at IS NULL;"
   #    ожидаем 0 — иначе 0055 не отработала или появились новые такие строки
   ```

8. **Очереди и фоновые циклы живы.** `GET /api/v1/admin/health` — очереди без растущего числа
   failed. **Проверять надо два процесса, а не один.**

   В процессе **api** по таймеру крутятся **четыре** цикла СЭД (`grep setInterval` по
   `apps/api/src/modules/docflow/`): `acquaintance-gate.service.ts` (открытие гейтов
   предварительного ознакомления, 60 с), `docflow-deadline-outbox.service.ts` (разбор
   outbox-очереди уведомлений о сроках), `exchange-sender.service.ts` и
   `exchange-receiver.service.ts` (обмен, период — `DOCFLOW_EXCHANGE_POLL_SECONDS`, по
   умолчанию 60 с). Безусловно стартуют **первые два**; оба цикла обмена стартуют **только при
   настроенном контуре** — `onModuleInit` выходит сразу, если `registry.isConfigured` ложь, и
   `sendDue()` / `receiveAll()` перепроверяют это на каждом проходе. Без `DOCFLOW_EXCHANGE_DIR`
   (штатное состояние — см. п. 1 и раздел «Не проверено») таймеров обмена нет вовсе, и их
   отсутствие в логах поломкой не является.

   В процессе **worker** живёт сам ежедневный проход по срокам — очередь BullMQ `deadlines`,
   repeatable job `0 8 * * *` tz `Asia/Dushanbe` (`apps/worker/src/queues/deadlines/`). Именно он
   пишет строки в `app.notification_outbox`; api их только разбирает. Отсюда практический вывод,
   ради которого этот пункт и существует: **поднявшийся api гарантирует разбор очереди, но не её
   наполнение** — при лежащем worker таймер в api тикает, а напоминаний не рождается ни одного,
   и внешне это неотличимо от «сроков нет». Проверять `dc ps worker` и суточные строки
   `deadline sweep` в его логе.

   Отдельной очереди BullMQ для api-шных циклов нет (в `packages/shared/src/queues/index.ts`
   очередей `dispatch`/`exchange` не существует).

9. **Права не поехали.** Под ролью `employee` (у неё из СЭД только `docflow.use` + `docflow.create`)
   убедиться, что документ с грифом ДСП не виден и не открывается по прямой ссылке. ДСП =
   allow-list ∩ `docflow.confidential.view`, проверка серверная.

## 5. Откат

### 5.1. Чего не существует

**Down-миграций нет.** drizzle-kit их не генерирует, и в `packages/db/migrations/` их нет — там
только `*.sql` вперёд и `meta/_journal.json`. Команды «откатить последнюю миграцию» в
`packages/db/package.json` тоже нет. Полный список скриптов там: `build`, `typecheck`, `lint`,
`test`, `clean`, `generate`, `migrate`, `seed`, `seed:e2e`, `seed:perf`, `seed:perf:docs`,
`backfill:docflow-files`, `load:crosswalk`, `load:incidents`, `load:casualties` — ни один из них не
откатывает схему, а `seed*` наоборот наполняют базу (`seed:perf:docs` генерирует нагрузочные
документы СЭД). В окне обслуживания на проде из этого списка запускают только `migrate` и
`backfill:docflow-files`. Любой, кто скажет «просто откати миграцию», предлагает написать
обратный SQL руками прямо сейчас — по таблице §3 видно, для каких шагов это в принципе невозможно.

### 5.2. Что откат означает на самом деле

Есть ровно два пути.

**Путь А — восстановление из бэкапа.** Полная процедура — `docs/runbook-backup.md`
§Реальное аварийное восстановление. Возвращает БД и тома на момент снапшота. **RTO — 4 часа,
RPO — 24 часа** (`docs/runbook-backup.md`, шапка). Практически:

```bash
dc stop api worker
# восстановление — плоским docker run, НЕ через `dc run`: сервис backup монтирует тома :ro
docker run --rm --network cuks_default --env-file .env \
  -v cuks_backupdata:/repo \
  -v cuks_miniodata:/data/minio -v cuks_geoserverdata:/data/geoserver \
  -v cuks_ca_data:/data/ca -v cuks_caddy_data:/data/caddy \
  cuks-backup restore.sh <snapshot-id>
git checkout <версия-кода-ДО-обновления>   # записана в §1.2
dc build api worker caddy
dc up -d api worker caddy
docker run --rm --network cuks_default --env-file .env \
  -v cuks_miniodata:/data/minio:ro cuks-backup restore-verify.sh
```

Код обязательно откатывается вместе с базой: новый код на старой схеме не запустится осмысленно.

**Путь Б — исправление вперёд (fix-forward).** Новая миграция поверх, новый релиз. Для аддитивных
проблем это почти всегда быстрее и безопаснее, чем путь А: он не отматывает **всю** работу
организации за время с момента снапшота. Если сломался конкретный экран или конкретный расчёт, а
регистрация идёт — выбирайте Б.

**Как выбирать.** Восстановление из бэкапа стирает всё, что сделано после снапшота: все
зарегистрированные за это время документы, резолюции, подписи, ознакомления. Если после обновления
организация успела поработать хотя бы час, путь А сам по себе является потерей данных, и решение о
нём принимает владелец данных со стороны заказчика (§1.6), а не дежурный инженер.

### 5.3. Точки невозврата

Ниже — то, чего **не отменит ни один restore**, потому что след ушёл за пределы системы или
затирает состояние необратимо.

1. **Выданные регистрационные номера — и особенно те, что уже на бумаге.** Восстановление на
   вчерашний снапшот вернёт счётчики `journal_counters` назад. Документы, зарегистрированные
   сегодня, из БД исчезнут — но их номера уже проставлены на исходящих письмах, которые ушли из
   здания, и на входящих штампах. После восстановления следующая регистрация выдаст номер,
   **который уже существует на бумаге**, и узнает об этом только организация, получившая два
   письма с одним номером. Это единственное состояние СЭД, которое нельзя пересчитать из
   документов, — поэтому `restore-verify.sh` проверяет счётчики отдельно (§4.4). **После любого
   восстановления счётчики нужно сверить с бумажным журналом и при необходимости поднять вручную
   выше максимального выданного номера, до того как пустить пользователей.**

2. **Отправленные документы.** `document_dispatches` фиксирует отправку, но отправка уже
   состоялась: письмо доставлено, конверт ушёл, файл записан в `out/` каталога обмена и, возможно,
   уже забран принимающей стороной. Restore вернёт таблицу в состояние «не отправлено» — и система
   предложит отправить то же самое второй раз. Ни один restore не отзывает письмо. Перед тем как
   пускать пользователей после восстановления, сверьте `document_dispatches` со списком фактически
   отправленного за период.

3. **Каталог обмена рассинхронизируется с базой.** Штатный файловый адаптер при подтверждении
   переносит конверт из `in/` в `done/`/`rejected/`. Каталог обмена **не входит в бэкап**
   (см. §1.1): restore отматывает `document_exchange_inbound`, а папки — нет. Сообщения, принятые
   между снапшотом и восстановлением, окажутся потеряны с обеих сторон — в базе их уже нет, из
   `done/` они сами не вернутся. Восстанавливать их придётся вручную, перенося конверты обратно
   в `in/`.

4. **Акты о выделении к уничтожению и снимки сроков хранения.** Здесь важно быть точным: в этом
   релизе выбытие **логическое** — `executeBatch` только проставляет
   `disposition_status='executed'`, `disposed_at`, `disposed_by`; из хранилища ничего не удаляется,
   и ни один путь кода в этом релизе удалить не может. Значит, в самой БД шаг откатывается
   восстановлением. Необратимо другое: **акт, подписанный на бумаге и ушедший в архивное
   учреждение, не отзывается restore'ом**, а снимок срока хранения, зафиксированный при подшивке
   (`retention_until`, `retention_months`, `is_permanent` — их проставляет `archive` в момент
   архивирования), при возврате документа из архива **сбрасывается намеренно**, чтобы не тащить
   срок от отменённой подшивки: `restore` в `archive.service.ts` ставит `archived_at`,
   `archived_by`, `retention_until`, `retention_months` в `NULL`, а `is_permanent` — в `false`
   (эта колонка `boolean NOT NULL DEFAULT false`, `NULL` в ней невозможен, так что искать сброшенные
   документы запросом `WHERE is_permanent IS NULL` бесполезно — он всегда пуст). Кто и
   когда подшил — восстановится; а вот `archived_by` для документов, подшитых до обновления,
   не появится никогда: миграция `0055` намеренно оставила его `NULL`, потому что этого никто
   не знает, и выдумывать имя в архиве хуже, чем признать пробел.

5. **Правовые запреты (`legal_hold`), снятые или поставленные после снапшота.** Restore вернёт
   флаг к состоянию на момент снапшота. Запрет, поставленный по требованию надзорного органа
   сегодня, после восстановления вчерашнего снапшота **исчезнет**, и документ снова станет
   кандидатом на выделение. Список установленных запретов нужно сверять после каждого
   восстановления отдельно — он приходит извне системы и в ней не выводится.

6. **Уведомления, ознакомления и подписи, уже увиденные людьми.** Резолюция, которую руководитель
   подписал, и лист ознакомления, который сотрудники подписали, после restore исчезнут из системы,
   но не из памяти участников. Люди будут считать работу сделанной. Об откате нужно объявить
   явно — молчаливый restore порождает документы, которые «точно подписывали», а в системе их нет.

7. **Ключ УЦ.** Здесь наоборот — хорошая новость, но её надо знать: том `ca_data` входит в снапшот,
   поэтому ранее выпущенные подписи после восстановления остаются проверяемыми
   (`docs/runbook-backup.md`, §Реальное аварийное восстановление). Потеря `RESTIC_PASSWORD` — вот
   она невосстановима абсолютно: без него ни один бэкап не расшифровывается.

### 5.4. Если откатывать поздно, а мигрировать нельзя

Промежуточное состояние существует и им стоит пользоваться: остановить `api` и `worker`
(`dc stop api worker`), оставив `caddy`, `postgres`, `minio` — БД не меняется, файлы на месте,
пользователи видят ошибку сети вместо порчи данных. Это даёт время принять решение, не накапливая
новых регистраций, которые потом придётся выбирать между потерей и дублем номеров.

## 6. Правила

Не рекомендации — инварианты (`CLAUDE.md` §2, `docs/plan/sed_plan_implementation.md` §11).

1. **Никогда не редактировать уже применённую миграцию.** Ни «поправить опечатку», ни «дописать
   недостающий индекс». drizzle-kit сверяет применённое по своей служебной таблице; на вашей машине
   исправленный файл не переприменится, а на чистой установке даст другую схему — и две установки
   разъедутся молча. Всё исправляется **только новой миграцией**.

2. **`when` в `meta/_journal.json` должен строго возрастать.** Это порядок применения. Обратите
   внимание: у `0046`…`0057` значения `when` проставлены вручную с шагом 1000
   (`1785540000000`…`1785540011000`), у `0058`…`0060` — сгенерированы drizzle-kit. Если вы
   добавляете миграцию вручную или переносите её между ветками, **проверьте, что новый `when`
   больше последнего** (сейчас последний — `1785582087890`, `0060_modern_stellaris`) и что `idx`
   продолжает нумерацию без дыр. Убывающий `when` перемешает порядок и применит миграцию до той,
   от которой она зависит.

3. **Схема меняется только через drizzle-kit.** `pnpm db:generate` из изменённой схемы в
   `packages/db/src/schema/**`, затем ручная вычитка сгенерированного SQL. Никаких `ALTER TABLE`
   руками в проде: следующая генерация не будет знать о вашем изменении и сгенерирует конфликт.
   Рукописные миграции допустимы там, где drizzle не умеет (партиционирование, generated-колонки),
   но тогда файл, запись в журнале и снимок схемы должны быть согласованы вручную и целиком.

4. **Expand → backfill → enforce → cleanup, и каждый шаг в своём релизе.**
   - *expand*: новые nullable-колонки, новые таблицы, новые индексы — старый код продолжает
     работать;
   - *backfill*: отдельный идемпотентный скрипт с `--dry-run`, батчами и возможностью
     продолжить с места остановки (образец — `backfill:docflow-files`, §2.5);
   - *validate*: counts, orphan FK, выборочная сверка;
   - *enforce*: `NOT NULL`, `CHECK`, новые политики — **только после** успешного бэкфилла;
   - *cleanup*: удаление устаревших колонок — **отдельным релизом**, после подтверждения, что их
     больше никто не читает.

   `0053` и `0055` это правило нарушают: они выполняют бэкфилл одним `UPDATE` внутри миграции, без
   батчей и курсора. Так сделано осознанно (объёмы на текущих установках это позволяют), но
   повторять этот приём на растущей таблице не следует — на большом архиве такой `UPDATE`
   удерживает блокировки на всех затронутых строках до конца.

5. **Перед необратимым шагом — бэкап и проверка восстановления.** Не бэкап, а именно проверка:
   бэкап без проверенного восстановления бэкапом не считается (`docs/runbook-backup.md`).

6. **Крупные индексы — способом, не блокирующим прод, если версия позволяет; решение записать.**
   В этом треке правило не соблюдено: `0056` строит GIN-индекс без `CONCURRENTLY`, потому что он
   создаётся сразу после пересоздания генерируемой колонки, которая всё равно берёт
   `ACCESS EXCLUSIVE` на всю таблицу. Отсюда требование окна с остановкой api (§2). Для будущих
   индексов на `documents` этот компромисс не переиспользовать — там `CONCURRENTLY` уместен.

7. **Порядок развёртывания: аддитивная схема → api/worker → web → бэкфилл → ограничения.** Здесь
   web вшит в образ caddy и едет вместе с api; помнить об этом при планировании любого шага, где
   фронт и бэк должны разъехаться по времени.

## Не проверено / открытые вопросы

Честно перечислено, чтобы никто не принял это за проверенный факт:

- **Имя служебной таблицы drizzle-kit** в репозитории нигде не зафиксировано и в
  `drizzle.config.ts` не переопределено. Поэтому §1.3 не называет её, а показывает, как её найти
  запросом. Подставьте найденное имя в свои чек-скрипты один раз и зафиксируйте.
- **Длительность миграции `0056`** на реальном объёме здесь не измерялась. Оценивайте по
  `pg_total_relation_size('app.documents')` (§1.4) и, если объём значимый, прогоняйте миграцию на
  копии прод-базы с секундомером **до** окна.
- **Каталог обмена (`DOCFLOW_EXCHANGE_DIR`) не описан в `compose.prod.yaml`** и не входит в
  `backup.sh`. Штатное состояние контура обмена — «не настроен». Если заказчик его настраивает,
  вопросы «где лежит каталог, кто его бэкапит и как он переживает restore» надо решить отдельно —
  готового ответа в коде нет.
- **Кому достаётся `docflow.journals.manage` — проверять по коду релиза, а не по этому документу**
  (см. §1.7). В текущем коде его выдают `clerk` и `platform_admin` (и `superadmin` через wildcard),
  но в более ранних сборках трека — ни один шаблон роли, поэтому на конкретной установке
  результат зависит и от версии кода, и от того, прогоняли ли на ней сид. Единственный источник
  истины —
  `ROLE_TEMPLATES` в `packages/shared/src/permissions/index.ts`. То же касается утверждений
  `docs/modules/11-docflow.md` о правах `platform_admin`: спека и код по этому пункту расходились,
  и верить нужно коду.
- **Роли «архивариус» в системе нет вовсе.** Архивные права (`docflow.archive.hold`,
  `docflow.archive.dispose`) закреплены за шаблоном `chief` (Руководитель). Если в процедуре
  вашей организации есть архивариус, он описывается **правом**, а не ролью, — и вопрос «кто
  подписывает акт о выделении к уничтожению» решается назначением `docflow.archive.dispose`
  конкретному человеку. Готового ответа в коде нет.
